# 滑窗（pipeline_window）隔离装置兼容性验证方案

> 状态：**未验证**。`pipeline_window` 默认 1（停等），开启前必须完成本验证。
> 结论（通过/不通过）确认后回填本文档并更新 README/AGENT.md。

## 1. 背景

停等协议是隔离装置"一问一答"约束逼出来的（协议仅允许每帧回 1 字节 0xff/0x00）。
滑窗（V1.4 起，`sender.pipeline_window`）在协议层兼容——每帧仍对应一个响应字节、
按序写回——但同一连接上会有 W 个请求在途。**软件自测（本地回环）无法覆盖物理装置
的行为**，必须实机验证。

## 2. 装置侧确认项（先问厂商，后实测）

| # | 确认项 | 通过标准 |
|---|---|---|
| 1 | 同一 TCP 连接上连续写多个请求（不读应答），装置是否全部转发 | 全部到达 receiver |
| 2 | 多个在途请求的应答是否按请求顺序返回、字节数 1:1 | 按序、不多不少 |
| 3 | 装置内部缓冲上限是否容纳 W×1MB 在途 | 帧长 1MB×W 不丢字节 |
| 4 | 0x00 后主动断开重连（V1.4.1 N1 修复行为）是否正常、有无重连频率限制 | 断开→重连→重发正常恢复 |
| 5 | 装置是否对"请求>应答"瞬时状态告警/审计异常 | 无告警或告警可接受 |

## 3. 实验室实测步骤

拓扑：`loadgen 写源库 → sender(103) → 隔离装置 → receiver(171) → 目标库`。

1. 基线（停等）：`pipeline_window: 1`，用 bench/loadgen 压 60s，记录
   吞吐、`sync_delay_seconds`、`ack_fail`、`retry_total`、目标库 count。
2. receiver 侧确认 `tcp.max_inflight: 8`（默认即 8）。
3. sender 改 `pipeline_window: 4`，重启，压同样 60s。
4. 观察：
   - 两端计数零丢失（源 count == 目标 count，允许幂等重复写入不计）；
   - 日志无 `send failed` / `ack wait failed` 刷屏；
   - 吞吐是否接近基线 ×W（受查询/组帧/写库瓶颈约束，不达标也可能正常，
     但**吞吐必须 ≥ 基线**）；
   - `ack_fail`/`retry_total` 不异常增长。
5. 故障注入：压测中途停 receiver 15s 再恢复，确认 go-back-N 重传、
   WAL 积压清空、无丢失。
6. 边界：`pipeline_window: 8` 重复步骤 3-5。

## 4. 通过标准

- 步骤 3-6 全部通过、零丢失、无连接抖动；
- 厂商对 §2 的 5 项无否决项。

## 5. 回滚

`pipeline_window: 1` + 重启即回停等（协议/WAL 格式不变，回滚零成本）。
