# A4/V1.6 基准测试报告（2026-08-15，本机 Docker）

## 1. 环境与拓扑

- 硬件：AMD Ryzen 7 4800H（8C/16T）、19GB RAM、WSL2 + Docker 29.6；
- 源/目标 InfluxDB 1.8 容器（各一实例，端口 18086/18087），源侧 `[subscriber]`
  `flush-interval=200ms`、`write-buffer-size=1000`；
- sender/receiver 为本仓 V1.6.0 二进制；链路与订阅推送各挂一个字节计数代理
  （`bench/linkproxy`）测带宽；
- 压测：`bench/loadgen`（telemetry 格式，plant/point 两个 tag，每点独立 ns 时间戳）；
- 每档：源/目标库重置、25s 压测、排空后计数；指标每 2s 采样。

## 3. 结论

1. **实时性（核心目标）**：订阅 fast-path 在所有档位把"新数据到达目标库"的延迟压到
   **0~1s**（flush 200ms + 传输 + 写库），而轮询路径受 watermark+查询+积压影响，
   5 万时 3~7s、10 万时 12~17s、负载越高差距越大——**订阅路径在高压下反而更稳**。
2. **带宽**：
   - 隔离链路：**zstd 只有 gzip 的 1/2~1/3**（5 万：1.2 vs 2.6Mbps；10 万：1.4~2.0 vs
     2.5~3.2Mbps），且发送端 CPU 略降；
   - 订阅推送（I 区内部 LAN，明文 LP）：约 34~65Mbps，正比于写入速率，不占隔离链路；
   - fast 与轮询两种获取方式在链路上的带宽特征一致（同一编码管线）。
3. **零丢失**：5 万/10 万档目标计数与写入量精确一致；15/20 万档受本机源库写入上限
   （~84-120k 点/s，容器+loadgen 双瓶颈）限制，同步侧全程无丢失、无重试异常。
4. **本机瓶颈定位**：源库容器写入能力是 15 万以上的天花板；10 万档 fast 模式出现
   WAL 积压（pending 峰值 100~160 帧）说明目标库写+停等链路在本机接近饱和——真机
   （64 核/124G + 独立盘）上该瓶颈会大幅后移。
5. 测量注意事项：e2e 指标为秒级分辨率，"0s"即亚秒级延迟；调试期残留的 receiver
   进程曾占用端口跨档服务（数据面正确、指标首采样污染），本报告已剔除该因素。
