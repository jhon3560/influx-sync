## 2. 已确认的残余缺陷

### R3b（P2）：idName 反向数组无界增长

`idName []string` 用"追加空槽"方式扩容到 maxID，series 名清理时仅把槽位置空
（`d.idName[id] = ""`），**槽位本身永不回收**。R1 的目标场景（tag 近似唯一 ID、
每点一个新 series）下：

- series map：✅ 已修复（名字被删除，有界）；
- idName 切片：❌ 每退役 1 个 series 永久留下 16B 槽位——200k/s × 24h ≈ 170 亿槽
  ≈ 270GB，重新 OOM。R1 的"series 映射不再无界增长"目标只达成一半。

取证（临时测试，20 万 unique series 全驱逐后）：
`series=0 idRefs=0 idNameSlots=200000 (nextID=200000)`——槽位一个不少。

### R3a（P2）：重复登记双计引用 → series 名泄漏

`Add` 中 `idRefs[id]++` 在 `part[packed] = struct{}{}` **之前无条件执行**；同一
(series, ts) 被登记两次（客户端同 ts 重写 → 订阅推两次；或同批内重复行）时，
集合只有 1 个条目但计数为 2。驱逐时减 1 次后残留 1 → 该 series 名永远不清理。
取证：`refs after duplicate add: 2 (want 1)`，驱逐后 `series name leaked`。

## 4. 修复建议（改动极小）

1. **R3b**：`idName` 改为 `map[uint64]string`（清理时 `delete(d.idName, id)`）——
   内存与活跃 series 数成正比；或维护 ID 空闲链表复用 ID。
2. **R3a**：`Add` 中改为"仅在条目首次插入时计数"：
   ```go
   if _, exists := part[packed]; !exists {
       part[packed] = struct{}{}
       d.idRefs[id]++
   }
   ```
3. 回归测试：① 重复登记后驱逐，断言 series map 归零（R3a）；② N 个 unique series
   全驱逐后断言 `len(idName) == 0`（R3b，改 map 后语义）。
